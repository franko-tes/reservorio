Active Directory

DNS y LDAP

Protocolos

De qué trata

DNS y LDAP no autentican al usuario como Kerberos o NTLM, pero AD no funciona sin ellos:

  • DNS: permite al equipo encontrar los DC.
  • LDAP: es el protocolo con el que se consulta y se modifica el directorio.

Idea clave: DNS responde “¿dónde está el DC?”. LDAP responde “¿qué hay en el directorio?”. Para iniciar sesión, primero hace falta DNS (ver 03.1).

DNS: cómo se encuentra un DC

  • Puerto 53, TCP y UDP.
  • Los DC registran en DNS registros SRV, que asocian un servicio con los equipos que lo ofrecen.
  • Nombre del registro: _servicio._protocolo.dominio. Por ejemplo, este devuelve los DC del domain: 
    _ldap._tcp.dc._msdcs.techcorp.local

    Ahí, _ldap es el servicio, _tcp el protocolo y dc._msdcs.techcorp.local el dominio: _msdcs es la zona donde AD publica sus registros propios y dc agrupa los de los DC.

  • El registro lo hace el servicio Netlogon del DC al iniciar, con actualizaciones dinámicas.
  • Hay registros SRV para LDAP, para Kerberos (_kerberos._tcp, puerto 88) y para el Global Catalog.
  • Relevante: si el equipo no resuelve estos registros, no encuentra un DC y no puede pedir el TGT (ver 03.1).

Campos de un registro SRV

Priority
Se prueba primero el de menor valor.
Weight
Reparte la carga entre los de igual prioridad.
Port
El puerto del servicio.
Target
El nombre del equipo que lo ofrece.

LDAP: qué es

  • Es un protocolo estándar abierto (RFC 4511) para consultar y modificar un directorio. AD lo usa como protocolo de acceso.
  • Lo usan las herramientas de administración, las aplicaciones y los propios equipos del domain.

Puertos

389
LDAP. Puede cifrarse con STARTTLS (Start TLS, iniciar TLS; TLS es Transport Layer Security): la conexión empieza sin cifrar y el cliente pide pasar a TLS dentro de la misma conexión.
636
LDAPS, LDAP dentro de SSL/TLS. El cifrado empieza al conectar.
3268
Global Catalog (LDAP). Solo en los DC que son Global Catalog (ver 02.3).
3269
Global Catalog sobre SSL/TLS.

Anatomía de una consulta

Una consulta LDAP indica tres cosas:

Base
Desde dónde buscar, con un DN (ver 02.2). Por ejemplo, dc=techcorp,dc=local.
Filtro
Qué objetos buscar. Por ejemplo, (&(objectClass=user)(sAMAccountName=bjones)).
Atributos
Qué datos devolver, como memberOf (ver 02.1).

Cómo se autentica (bind)

Antes de consultar, el cliente hace un bind: se autentica ante el DC, y las consultas de esa conexión se hacen con esa identidad y sus permisos. Hay tres clases de bind:

Anónimo
Sin credenciales.
Simple
El cliente envía usuario y password al DC en el propio mensaje, sin hash ni clave. Si la conexión no está cifrada, cualquiera que vea el tráfico puede leerlas. Con LDAPS, viajan dentro de un canal cifrado.
SASL
Simple Authentication and Security Layer. Es un marco que delega la autenticación en un mecanismo: Negotiate, Kerberos, NTLM o Digest. Con Kerberos o NTLM, la password no viaja (ver 03.1 a 03.4).

Firmado y channel binding

Son protecciones que se suman a una conexión LDAP para que no se puedan alterar los mensajes, leerlos ni reenviar la autenticación por otra sesión:

  • LDAP signing: firma los mensajes para detectar que no fueron alterados.
  • LDAP sealing: además de firmar, cifra los mensajes. Lo hace el mecanismo SASL, por ejemplo Kerberos, sin necesidad de TLS.
  • Si el DC exige el firmado, rechaza los bind SASL que no piden firma y los bind simples por conexiones no cifradas.
  • Channel binding: liga la autenticación SASL a la sesión SSL/TLS. Importa sobre todo con NTLM, para evitar que la autenticación se reenvíe por otra sesión. No aplica al bind simple.
  • Opciones del channel binding: con “Never”, el DC no lo valida; con “When supported”, se lo exige a los clientes que lo soportan y sigue aceptando a los que no; con “Always”, rechaza a los clientes que no lo envían.
  • Valores por defecto: el channel binding está en “Never” hasta Windows Server 2022, y el firmado es opcional hasta Windows Server 2019. En los despliegues nuevos de Windows Server 2025, el firmado se exige y el channel binding está en “When supported”. Las actualizaciones in situ mantienen la configuración que tenían.

Para no confundirse

  • LDAP siempre viaja en claro: no. Con LDAPS (o STARTTLS) o con sealing de SASL va cifrado. El firmado solo detecta alteraciones; no oculta el contenido.
  • La password nunca viaja por la red en AD: con Kerberos y NTLM, no. Con un bind simple de LDAP sí viaja, y solo está protegida si la conexión va cifrada.
  • LDAPS y LDAP signing son lo mismo: no. LDAPS cifra toda la conexión; el firmado solo protege la integridad.
  • DNS es solo para navegar: no. En AD es lo que permite encontrar los DC.
  • El puerto 3268 es otro protocolo: no. Es LDAP contra el Global Catalog.
