NTLM y hashes

Protocolos

De qué trata

En Windows hay tres cosas con nombres parecidos que se confunden:

  • Hashes guardados (LM y NT): el resultado de aplicarle un algoritmo de hash a la password. Se guardan en AD y en las bases locales.
  • NTLM: el protocolo de autenticación que usa el hash NT para probar quién es el usuario, con un desafío y una respuesta.
  • Credenciales en caché: una copia local para poder entrar al equipo sin DC.

Idea clave: Un hash es un dato guardado. NTLM es un protocolo que usa ese dato. No son lo mismo. Por eso en estos contenidos se dice “hash NT” y no “hash NTLM”, que mezcla las dos cosas.

Lo que se guarda

Hash NT

  • Es el resultado de aplicar el algoritmo MD4 a la password en UTF-16.
  • No usa salt: la misma password da el mismo hash en cualquier cuenta o equipo.
  • Con RC4, es la clave de Kerberos (ver 03.1).
  • Riesgo: quien obtenga un hash NT puede autenticarse con NTLM sin conocer la password (pass-the-hash), porque la respuesta NTLM se calcula a partir del hash.

Hash LM

  • Es el más viejo y débil: limita la password a 14 caracteres, la pasa a mayúsculas y la parte en dos mitades que se procesan por separado.
  • Hoy no se guarda por defecto.
  • Riesgo: los hashes LM que ya existían siguen guardados hasta que la cuenta cambie su password.

Credenciales en caché (MSCache2)

  • El equipo guarda una verificación de la password de los últimos 10 usuarios del domain que iniciaron sesión, para poder entrar sin DC (ver 03.1).
  • No es el hash NT, y no sirve para pass-the-hash.
  • Riesgo: quien acceda al equipo puede intentar descubrir las passwords por fuerza bruta. Microsoft menciona como contramedida poner el valor en 0, a costa de que no se pueda entrar sin DC.

NTLM paso a paso

NTLM prueba que el usuario conoce la password, sin enviarla, con un desafío y una respuesta.

1. NEGOTIATE
Cliente → servidor. El cliente indica qué soporta.
2. CHALLENGE
Servidor → cliente. Envía un número aleatorio, el desafío.
3. AUTHENTICATE
Cliente → servidor. Devuelve una respuesta calculada con el hash NT y el desafío.
4. Validación
Si la cuenta es del domain, el servidor no puede verificarla solo, porque no tiene el hash. Envía el desafío y la respuesta al DC, que la comprueba con el hash guardado. Si la cuenta es local, se verifica contra la base local.

NTLM no usa tickets: cada autenticación repite el desafío y la respuesta. Y no tiene autenticación mutua: el servidor no prueba su identidad.

Versiones

  • NTLMv1: usa DES y es débil.
  • NTLMv2: usa HMAC-MD5 e incluye un desafío del cliente, un timestamp y el nombre del domain. Es más resistente que NTLMv1: el timestamp y el desafío del cliente dificultan reutilizar una respuesta.
  • Por defecto: Windows Server 2008 R2 y posteriores envían solo NTLMv2.
  • Riesgo: una respuesta capturada no sirve para pass-the-hash, pero se puede intentar descubrir la password por fuerza bruta, o reenviar la autenticación a otro servidor en tiempo real (relay).

NTLM frente a Kerberos

Cómo prueba la identidad
NTLM, con desafío y respuesta a partir del hash NT. Kerberos, con tickets (ver 03.2).
Quién valida
En NTLM, el DC en cada autenticación si la cuenta es del domain, o el propio equipo si es local. En Kerberos, el KDC emite tickets y el servicio los valida.
Autenticación mutua
NTLM no. Kerberos sí, cuando se pide.
Preferencia
Microsoft prefiere Kerberos en entornos AD y recomienda auditar y restringir NTLM. Sigue haciendo falta en equipos de workgroup, en el inicio de sesión con cuentas locales, y cuando no se puede usar Kerberos (ver 03.1).

Eventos y señales

Evento 4776

En el DC, cuando valida credenciales con NTLM (éxito o falla). Para cuentas locales, se genera en el propio equipo. Solo NTLM: no registra Kerberos (ver 03.3). Subcategoría: Audit Credential Validation.

Logon Account
La cuenta cuyas credenciales se validaron.
Source Workstation
El equipo de origen. El destino no se registra.
Error Code
0x0 = éxito.

En el 4624 y el 4625, el campo Package Name indica NTLM V1, NTLM V2 o LM (ver 03.3). Un 4624 con Negotiate más un 4776 correspondiente en el DC indican que se usó NTLM.

Códigos de interés del 4776

0xC000006A
Password incorrecta.
0xC0000064
El usuario no existe.
0xC0000234
Cuenta bloqueada.

Escenario típico: un acceso a un share con NTLM deja un 4776 en el DC y un 4624 tipo 3 en el servidor, con Package Name NTLM V2.

Señales

  • Riesgo: ráfagas de 4776 con 0xC000006A (posible fuerza bruta) o con 0xC0000064 (posible enumeración de cuentas).
  • Riesgo: Package Name NTLM V1 o LM en un 4624.
  • Riesgo: NTLM para cuentas o sistemas que no deberían usarlo.
  • Relevante: el 4776 no registra el destino. Para saber a qué equipo se accedió, hay que mirar el 4624.

Para no confundirse

  • “Hash NTLM” y “hash NT” son lo mismo: no del todo. El hash NT es el dato guardado. NTLM es el protocolo.
  • NTLM envía el hash NT: no. Envía una respuesta calculada con el hash y el desafío.
  • Una respuesta NTLM capturada sirve para pass-the-hash: no. Sirve para intentar descubrir la password por fuerza bruta, o para relay.
  • NTLM ya no se usa: no. Sigue haciendo falta en workgroups y en inicios de sesión con cuentas locales.
  • Las credenciales en caché permiten pass-the-hash: no. No son el hash NT.
