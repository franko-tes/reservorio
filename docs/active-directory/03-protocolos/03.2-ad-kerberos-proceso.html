Kerberos, el proceso paso a paso

Protocolos

De qué trata

Kerberos funciona en tres intercambios, cada uno con un pedido y una respuesta. En cada uno cambia quién habla con quién y con qué clave se cifra lo que viaja (ver 03.1 para las piezas).

  • AS (mensajes 1 y 2): el cliente prueba quién es y recibe un TGT.
  • TGS (mensajes 3 y 4): el cliente usa el TGT para pedir un ticket de un servicio concreto.
  • AP (mensajes 5 y 6): el cliente presenta el ticket al servicio.

Idea clave: Los dos primeros intercambios son contra el KDC. Solo el tercero es contra el servicio, y el KDC no participa.

Antes de empezar

El usuario escribe su password al iniciar sesión. El equipo la convierte en una clave (la clave del usuario) y la guarda en memoria. Esa clave es la que se usa en el primer intercambio. La password en sí no se envía.

Intercambio 1: AS (el TGT)

1. AS-REQ
Cliente → KDC. Lleva la identidad del usuario, el servicio que se pide (el propio krbtgt) y los datos de preautenticación: un timestamp cifrado con la clave del usuario.
El KDC
Busca al usuario en AD, toma su clave y descifra el timestamp. Si descifra bien y la hora es válida, sabe que quien pide conoce la password.
2. AS-REP
KDC → cliente. Lleva dos partes. Una copia de la logon session key, cifrada con la clave del usuario, que el cliente puede leer. Y el TGT, que contiene otra copia de la session key y los datos de autorización del usuario, cifrado con la clave de krbtgt, que el cliente no puede leer.
El cliente
Descifra la session key con su clave y guarda la session key y el TGT en su caché de tickets.

Intercambio 2: TGS (el ticket de servicio)

3. TGS-REQ
Cliente → KDC. Lleva el servicio al que quiere acceder, identificado por su SPN (ver 02.4), un authenticator cifrado con la logon session key, y el TGT.
El KDC
Descifra el TGT con la clave de krbtgt y obtiene la logon session key y los datos de autorización. Con esa session key descifra el authenticator y lo valida. Después crea una service session key nueva, para que cliente y servicio compartan.
4. TGS-REP
KDC → cliente. Lleva dos partes. Una copia de la service session key, cifrada con la logon session key, que el cliente puede leer. Y el ticket de servicio, que contiene otra copia de la service session key y los datos de autorización, cifrado con la clave del servicio, que el cliente no puede leer.
El cliente
Guarda ambos en su caché.

Intercambio 3: AP (el servicio)

5. AP-REQ
Cliente → servicio. Lleva el ticket de servicio, un authenticator cifrado con la service session key, y un indicador de si el cliente quiere mutual authentication.
El servicio
Descifra el ticket con su propia clave y obtiene la service session key y los datos de autorización. Con esa session key descifra el authenticator y valida el timestamp. Si es válido, acepta al cliente.
6. AP-REP
Servicio → cliente, solo con mutual authentication. El servicio devuelve el timestamp del authenticator del cliente, cifrado con la service session key. El cliente lo descifra y lo compara con el original. Si coincide, sabe que el servicio es el verdadero, porque solo quien tenía la clave del servicio pudo abrir el ticket.

Las dos session keys

Logon session key
La conocen el cliente y el KDC. Se usa para pedir tickets de servicio.
Service session key
La conocen el cliente y el servicio (y el KDC, que la creó). Se usa entre cliente y servicio.

El cliente carga con dos tickets que no puede leer. Solo los transporta.

Por qué hay preautenticación

Sin ella, cualquiera podría pedir al KDC una respuesta AS-REP para el usuario que quisiera, y esa respuesta ya vendría cifrada con la clave de ese usuario. Con eso se podría intentar adivinar la password sin conectarse más. Con preautenticación, el KDC solo responde si el pedido ya viene cifrado con esa clave.

  • Riesgo: existe una opción de cuenta que la desactiva (“Do not require Kerberos preauthentication”). Una cuenta así deja de tener esa protección.

La hora y los timestamps

Los authenticators llevan timestamp y sirven también contra repeticiones: un mensaje copiado y reenviado lleva una hora vieja. Si la diferencia entre el reloj del cliente y el del DC supera la tolerancia, la autenticación falla. El valor por defecto es 5 minutos. Por eso la hora de los equipos del domain se sincroniza con la jerarquía del domain, que parte del PDC Emulator (ver 02.3).

Cuánto duran los tickets

Por defecto, en la política de Kerberos del domain:

TGT
10 horas. Dentro de un plazo de renovación de 7 días puede renovarse. Pasado ese plazo, hay que autenticarse de nuevo con un DC.
Ticket de servicio
600 minutos (10 horas). Al vencer hay que pedir uno nuevo para abrir conexiones nuevas. Las conexiones ya autenticadas no se cortan.
  • Riesgo: con un valor de 0, los tickets no vencen.
  • Riesgo: un ticket ya emitido sigue valiendo hasta que vence. Si una cuenta se deshabilita, puede conservar acceso hasta ese momento.

Los datos de autorización

Los dos tickets llevan los datos de autorización del usuario, que el KDC copia del TGT al ticket de servicio. Con ellos el servicio sabe quién es el usuario y de qué grupos es miembro. Por eso un cambio de grupos se refleja recién cuando el usuario obtiene un TGT nuevo, por ejemplo al volver a iniciar sesión.

Dónde encajan los ataques

  • Riesgo, Kerberoasting: se pide un ticket de servicio (mensaje 3) y el que llega en el mensaje 4 se intenta descifrar sin conexión, porque está cifrado con la clave de la cuenta del servicio (ver 02.4).
  • Riesgo, tickets falsificados: quien tenga la clave de krbtgt puede fabricar un TGT, y quien tenga la clave de un servicio, un ticket de servicio.

Qué deja en los logs

Los intercambios AS y TGS dejan eventos en los DCs: uno cuando se pide un TGT y otro cuando se pide un ticket de servicio.

Para no confundirse

  • El KDC decide si el usuario puede acceder al servicio: en general, no. Autentica y entrega el ticket; la decisión de acceso la toma el servicio, con los permisos. Las authentication policies pueden hacer que el KDC niegue un ticket (ver 02.9).
  • La session key viaja en claro: no. Siempre viaja cifrada: una copia con una clave que lee el cliente y otra dentro de un ticket que no lee.
  • En el tercer intercambio interviene el KDC: no. El cliente habla directo con el servicio.
  • El authenticator es una password: no. Es un timestamp cifrado que prueba que el cliente conoce la session key.
