Kerberos, las piezas

Protocolos

De qué trata

Kerberos es el protocolo de autenticación por defecto para las cuentas del domain desde Windows 2000. Es un estándar abierto (RFC 4120). En vez de enviar la password por la red, trabaja con tickets: el usuario prueba quién es una vez y después usa tickets para acceder a los servicios.

Interviene en dos momentos:

  • Al iniciar sesión en un equipo del domain: el equipo obtiene un TGT del KDC en nombre del usuario.
  • Al acceder a un servicio (un share, una web interna, una base de datos): se usa el TGT para pedir un ticket de ese servicio.

Idea clave: La password no viaja por la red. Se usa para derivar una clave, y con esa clave se cifra la prueba de identidad. El inicio de sesión en el equipo es el primer paso de Kerberos.

Los tres actores

Cliente
El usuario, a través del equipo desde el que trabaja.
KDC
Key Distribution Center. Corre en cada Domain Controller y usa AD como base de cuentas. Es un solo proceso con dos servicios: el AS (Authentication Service), que verifica al usuario y entrega el TGT, y el TGS (Ticket-Granting Service), que con un TGT válido entrega los tickets de servicio.
Servicio
Lo que el cliente quiere usar. Está asociado a una cuenta y a un SPN (ver 02.4). Un equipo del domain también es un servicio, con su propia cuenta de equipo.

Quién tiene qué clave

Clave del usuario
Se deriva de su password. La conocen el usuario y el KDC.
Clave de krbtgt
Se deriva de la password de la cuenta krbtgt. La conoce solo el KDC. Un RODC tiene la suya propia (ver 02.3).
Clave del servicio
Se deriva de la password de la cuenta del servicio. La conocen el servicio y el KDC.
Session keys
Las genera el KDC en cada intercambio. Las reciben solo las partes que corresponden.

krbtgt es la cuenta del KDC. Se crea sola con el domain, no se puede borrar ni renombrar, y su password se asigna automáticamente.

Los dos tickets

TGT
Ticket-Granting Ticket. Es la credencial de sesión. Se cifra con la clave de krbtgt, así que el cliente lo guarda pero no puede leerlo. Solo sirve para pedir tickets de servicio.
Ticket de servicio
Es el ticket para un servicio concreto. Se cifra con la clave del servicio, así que el cliente tampoco lo puede leer. Solo lo lee el servicio.

Es común ver “TGS” usado para las dos cosas. Acá TGS es el servicio del KDC y ticket de servicio es el ticket que entrega.

Vocabulario de mensajes

AS-REQ / AS-REP
El cliente pide un TGT y el KDC responde.
TGS-REQ / TGS-REP
El cliente pide un ticket de servicio y el KDC responde.
AP-REQ / AP-REP
El cliente presenta el ticket al servicio; el servicio responde si hay mutual authentication.

Puerto

88, TCP y UDP. Es una forma habitual de ubicar DCs en un escaneo de red.

Cuándo se usa Kerberos y cuándo no

  • Con un DC alcanzable: el inicio de sesión usa Kerberos. El equipo tiene que encontrar un DC por DNS y tener la hora sincronizada.
  • Sin DC alcanzable (por ejemplo, una notebook sin VPN): no se puede pedir el TGT. Windows permite entrar con las credenciales en caché (MSCache2).
  • Sin Kerberos posible: por ejemplo, si se accede a un servicio por IP en vez de por nombre, o si el servicio no tiene SPN. En general se cae a NTLM.

Para no confundirse

  • La password se envía cifrada al KDC: no. Se usa para derivar una clave que cifra una prueba; la password nunca viaja.
  • TGT y ticket de servicio son lo mismo: no. El TGT da derecho a pedir tickets; el ticket de servicio da acceso a un servicio.
  • El cliente lee su TGT: no. Está cifrado con la clave de krbtgt.
  • El ticket de servicio se cifra siempre con el hash NTLM del servicio: solo con RC4. Con AES se usa una clave derivada de la password y un salt.
